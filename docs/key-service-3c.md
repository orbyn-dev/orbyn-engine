# Key service, step 3c: the binary, the log and the witness

A design note for review before any code. It plans what [key-service.md](key-service.md) calls "its own deployment, store, … the transparency log", on top of what has landed: 3a (`wrap_key_p256`, engine#40) and 3b (the `orbyn-keyservice` library: the `Hsm` trait, SoftHSM, certification, opening an envelope, `orbyn keyservice init`, engine#43). Nothing here changes a rule in key-service.md; where it must say something that file does not, it says so and asks.

## What 3c is, and is not

- **In:** a key service you can run (its own binary, database, mutual-TLS internal API and small public API), an append-only transparency log with the service-key map and an empty identity map, signed heads with a log key kept apart from the identities, and a minimal witness that cosigns them, with a test witness for CI.
- **Not in:** the recovery state machine and the cancel route (step 5), client wiring and the engine's recipient kind (step 4), the identity map's content and its VRF (the sharing work), and the off-machine audit sink (a small PR after 3c, below).

## 1. The binary and its deployment

**Crates.**

| Crate | Owns | Runs on |
| --- | --- | --- |
| `orbyn-translog` (new) | The pure log: RFC 9162 Merkle tree, the prefix-tree map, every proof and its verifier, and (in the PRs that first need them) the canonical entry and head encodings. No IO. | Key service and devices (native and WebAssembly) |
| `orbyn-keyservice` (3b) | The HSM boundary, certification, opening one envelope. Gains a log key and the `LogHead` message (below). | Key service |
| `orbyn-keyservice-server` (new) | The `orbyn-keyservice` binary (`serve`, `migrate`, `init`), its Postgres store and migrations, the head builder, the internal and public APIs. | Key service |
| `orbyn-keyservice-client` (new, small) | The mutual-TLS client `orbyn-server` uses. Wired in step 4, built and tested here. | Server |
| `orbyn-witness` (new) | The cosigning library and a `orbyn-witness` binary; a `TestWitness` behind `test-support`. | A witness host; CI |

`orbyn keyservice init` stays in `orbyn-cli` and calls the same function the new binary's `init` calls, so the 3b interface does not move.

**Its own Postgres** (15 or later, tested on 17). The key service has its own database (in production its own instance, with credentials the record server and its operators do not hold). It has its own migrator and migrations directory (`crates/orbyn-keyservice-server/migrations/`), its own `_sqlx_migrations`, and **two database URLs and two roles**: `ORBYN_KEYSERVICE_MIGRATE_DATABASE_URL`, an owner role used only by `orbyn-keyservice migrate` (it owns the tables and creates the triggers), and `ORBYN_KEYSERVICE_DATABASE_URL`, a runtime role used by `serve` with only the grants it needs: `SELECT` and `INSERT` on the append-only tables, `UPDATE` only on the one column below, and no `TRUNCATE`, `DELETE` or DDL. It never reads the engine's database and the engine never reads its. CI uses a second database on the same Postgres service container, with both roles made by the test setup; the difference from production is isolation, not code.

**Tables** (all in the key service's database):

| Table | Holds |
| --- | --- |
| `service_keys` | `account_id` (primary key), `wrapped` (the private key under the KEK), `public` (33 bytes), `identity_version`, `statement`, `signature`, `created_at`. One row per account; rotating an account's key (key-service.md, *Rotating an account's service key*) adds a row and a log entry, step 5. |
| `log_entries` | `seq` (set under a lock, so it has no gaps and is the leaf position plus one; not a bigserial), `kind`, `chain_index`, `map` (`service` or `identity`), `map_key` (32 bytes), `prev_entry_hash` (the account's chain link), `payload` (canonical bytes), `leaf_hash`, `created_at`, `included_in_head` (null until a cosigned head covers it). Append-only: `TRUNCATE` is revoked and a `BEFORE TRUNCATE` trigger refuses it too; a `BEFORE UPDATE` trigger allows only `included_in_head` going from null to a value, and `DELETE` is refused. **These rules guard against bugs in the service, not against its operator**, who could drop the triggers; the real guarantee is the witness's check of every head (section 2), which no database rule can replace. |
| `log_nodes` | `(level, index)` → `hash` for the complete subtrees of the Merkle tree, written on append (O(log n) rows). |
| `map_nodes` | The nodes of both maps' path-compressed sparse Merkle trees, **content-addressed and immutable**: a node is stored under its own hash (a leaf holds a key and a value hash, a branch holds its bit index and its two children's hashes), and an update writes new nodes along one path and leaves the old ones, so an old head's roots keep their proofs and the table stays append-only. A map root is a node hash. |
| `heads` | `size`, `log_root`, `service_map_root`, `identity_map_root`, `time_ms`, `prev_head_hash`, `log_key_version`, `log_signature`, `cosignatures` (each witness's signature with its own signed time), `created_at`. Append-only, with the same triggers. |
| `rate_events` | `(action, subject, at)` for the public API's limits. A plain count over an index: the volumes are per address and per hour, so the engine's advisory-lock limiter is not needed. |

**Configuration** (environment, like the engine): `ORBYN_KEYSERVICE_DATABASE_URL`, `ORBYN_KEYSERVICE_MIGRATE_DATABASE_URL` (migrate only), `ORBYN_HSM_MODULE`, `ORBYN_HSM_SLOT`, `ORBYN_HSM_PIN` (3b), `ORBYN_KS_INTERNAL_BIND`, `ORBYN_KS_PUBLIC_BIND`, `ORBYN_KS_TLS_CERT`, `ORBYN_KS_TLS_KEY`, `ORBYN_KS_CLIENT_CA` (the CA that signs `orbyn-server`'s certificate), `ORBYN_KS_WITNESSES` (URLs), `ORBYN_KS_WITNESS_KEYS` (pinned public keys), `ORBYN_KS_WITNESS_THRESHOLD` (above half of the pinned witnesses; see below), `ORBYN_KS_LOG_KEY_VERSION`, `ORBYN_KS_ALLOWED_ORIGINS` (the planner's origins, for CORS).

**The internal API (mutual TLS), for `orbyn-server` only.** rustls on its own listener: the client certificate must chain to `ORBYN_KS_CLIENT_CA` and carry the SAN `orbyn-server`; anything else is refused at the handshake. No tokens on top of it. Certificates and keys reload on `SIGHUP`, so rotation needs no restart. In 3c:

- `POST /internal/v1/service-keys {account_id}` makes the account's service key and certifies it (`KeyService::new_account_key`), stores the row, appends the certification entry, and answers the public key, statement and signature. **Idempotent per account**: a second call returns the stored key and changes nothing.
- `GET /internal/v1/service-keys/{account_id}`: the stored public key, statement and signature, or 404.
- `GET /healthz`: the database and the HSM answer.

Recovery start, finish and escrow open arrive with step 5; the internal API grows then, behind the same listener.

**As built in PR 5** (`orbyn-keyservice-daemon`, whose binary is `orbyn-keyservice`, and `orbyn-keyservice-client`).

- **Commands.** `orbyn-keyservice serve` (the internal API), `migrate` (as the owner role: `ORBYN_KEYSERVICE_MIGRATE_DATABASE_URL`, `ORBYN_KEYSERVICE_RUNTIME_ROLE`), `init` (the KEK and identity 1 in the HSM; prints the identity's public key for clients to pin) and `init-log-key` (log key 1, printing its public key once; separate from `init` so `init` stays safe to refuse a second time and the log key can be made where `init` already ran). `serve` also takes `ORBYN_KS_IDENTITY_VERSION` (the only setting with a default, 1) and refuses to start without that identity in the HSM. Settings are environment variables only. **Everything these commands print for an operator is the designed text**, Account Designs v51 (orbyn-designs#45; frames `ks-help`, `ks-help-settings`, `ks-init`, `ks-init-log-key`, `ks-config-errors`, `ks-migrate`, `ks-serve`, `ks-reload`), in `messages.rs`, checked word for word by tests that copy each string from the design; errors go to stderr with exit status 1 and no setting's value is ever printed. The HSM's errors are typed (`HsmSetup`: module, slot, PIN, unreachable; or the PKCS#11 return code's name) so each gets its own message.
- **Mutual TLS.** TLS 1.3 only, ALPN `http/1.1`, a client without a certificate or with one that does not chain to `ORBYN_KS_CLIENT_CA` is refused at the handshake. **The name is checked again per endpoint**: every route is declared with the one identity allowed to call it (today the DNS name `orbyn-server` for all three), matched by rustls's own name matching, so a certificate the right CA signed for another client, or with a near name, is refused with **403 `forbidden` before the handler runs** on every endpoint. `router()` and `routes()` are built from one table (`ENDPOINTS`) and nothing else registers a route, and a test that works out what every path and verb must answer from the contract (404 for any path that is no route's, 405 for a route's other verbs) is run against the live server. TLS 1.3 only, **on both sides** (the client sets it too). `SIGHUP` (Unix) reloads the server certificate, its key and the client CA; new handshakes use the new settings, and **a successful reload ends every open connection after the request it is serving**, so a client whose certificate no longer chains has to connect again and is refused; a reload that fails (a bad file) keeps the settings in use and touches no connection. Independently, **a connection ends after 5 minutes or 1000 requests**, so a certificate that stopped being valid is not honoured for long even without a reload. On Windows there is no signal; restart to rotate. A client has 10 seconds for the handshake and for its headers, a request 30 seconds, at most 128 connections are served at once, and a failing accept is retried after a pause that grows to a second.
- **Answers.** `{"account_id", "identity_version", "public_key", "statement_hash", "signature", "entry_index"}`, each byte string in hex (the client refuses an answer whose `account_id` is not the one it asked about); `GET` adds `head_covers_entry`. `entry_index` is the certification's leaf index in the log. **201** when the call made the key and **200** when it returned one. Errors are `{"error": code}`: 400 `bad_request` (a body that is not `{"account_id": 32 hex digits}`; fields it does not read are ignored, so nothing a caller names is ever certified), 403 `forbidden`, 404 `not_found` (a read of an account with none), **409 `service_key_retired`** (create or read of an account whose key was retired: it gets no second key until a later change adds generations), 413 (a body over 1 KiB), 429 `rate_limited`, 503 `busy` (the store's lock or statement timeout) or `unavailable` (the HSM), 500 `internal`. `DELETE` is **204** whether or not there was a key.
- **What it cannot do.** The three routes are the whole surface, listed by `api::routes()` and checked against the live server by a test that tries open, derive, sign, unwrap and private-key paths with every verb and the right certificate. The HSM is never asked to unwrap a key or to sign anything but a service-key statement (the same test reads the spy). The store has no read of the wrapped key at all.
- **Store.** Migration `0002` makes `wrapped` nullable and adds `retired_at`, tied together by a check constraint; the update trigger now allows one change to a `service_keys` row, `wrapped` to null and `retired_at` to a time, once, and nothing else; the runtime role may write only those two columns. Create and retire each write the row and its log entry in **one transaction under the write lock** (`Store::get_or_create_service_key`, `retire_service_key`). **The HSM call runs outside the lock**: a hung HSM must not stop every writer. The order is look (no lock), make, take the lock, look again, insert only if there is still none; racing calls may each make a key, one is kept and the others are discarded (they exist only wrapped, in memory). An account retired **before it had a key** is recorded in `retired_accounts` (append-only) with no log entry, so a later create for it is refused with 409 like any retired account's. A certification is entry kind 1 on the service map under `service_account_map_key(public)`, its fields the 77-byte statement then the 64-byte signature (`certification_fields`); a retirement is kind 6, its fields the compressed key it retires. A retirement chains to the certification.
- **Limits.** 10 `POST`s per account an hour, **every POST counts** (a repeat that only returns the key too), counted in `rate_events` under a lock per account, with the same lock and statement timeouts as a write; older events of that account are deleted as it is counted.
- **Audit.** Each certification and retirement is passed to an `Audit` sink after it commits, as the account's map key and the time (no keys, no account id); a repeat is not reported. The default sink writes one structured line on the `audit` target. A crash between the commit and the line loses that line: the off-machine sink (below, later) is where that is closed.
- **Not in PR 5.** `GET /healthz` moves to PR 7 (a container health check cannot present a client certificate; it needs its own answer). **No process builds, signs, cosigns and stores heads yet.** `Store::build_head`, `KeyService::sign_head` and `orbyn_witness::client::Cosigner` exist, but nothing calls them in a loop, and the `RequestSource` a witness needs (the consistency proof from the stored subtrees and each entry's map path, replayed from the last head's roots, across the chain of stored heads) has no implementation outside tests. Until it lands, a running service never sets `head_covers_entry`. It is its own change, **before PR 6**, because the public API serves what it publishes.

**The public API (no client authentication), on its own hostname:**

- `GET /v1/log/head`: the newest cosigned head. `Cache-Control: max-age=60`, so the edge absorbs it.
- `GET /v1/log/consistency?from=&to=`: the consistency proof between two sizes.
- `GET /v1/log/entries?map_key=&after=`: an account's chain, with each entry's inclusion proof against a head.
- `GET /v1/log/lookup/{map_key}?map=service|identity`: the lookup proof: the map root's membership or non-membership proof for the key, the chain it commits to, and the head with its cosignatures.
- `GET /v1/keys`: the log and identity key versions in use, for operators checking what clients must pin. Clients do not trust this; they pin.

Rate limits as in key-service.md (lookups 60 per address an hour). CORS for `ORBYN_KS_ALLOWED_ORIGINS` only. A contract test fetches a head and a lookup proof across origins, so a blocked path fails CI.

**The cancel route is not in 3c.** A cancel names a recovery, and recovery does not exist yet; the route, its signature check and its log entry land with step 5. This is the one place this note departs from the list in key-service.md; see the questions at the end.

**Deployment.** `docker/keyservice.Dockerfile` builds only the key service crates (no engine code in the image and none of the key service in the engine's); the HSM module is mounted, never baked in. The compose file gains a `keyservice` profile with SoftHSM, a second Postgres and a witness, for development. The Docker CI job builds the image and checks its health.

## 2. The transparency log

**The tree.** RFC 9162 (certificate transparency v2): leaf hash `SHA-256(0x00 ‖ entry)`, node hash `SHA-256(0x01 ‖ left ‖ right)`, inclusion and consistency proofs as the RFC defines them. The test vectors are the RFC's. `orbyn-translog` holds the hashing and verification; the key service's `log_nodes` only stores what it computed.

**An entry** is a canonical, length-prefixed byte string: a version, the kind, the map and map key, the hash of the account's previous entry in this map (zero for the first, so each account has a hash chain), the time, and the kind's fields. Kinds in 3c: `1` service-key certification (the statement and its signature), `2` identity or KEK rotation. Reserved, not built: `3` to `5` recovery start, cancel and finish (step 5), and the identity map's statements (sharing).

**The two maps.** Both are verifiable maps over the same log, keyed by 32 bytes, each value the hash of the account's latest entry in that map and the chain length:

- the **service-key map**, keyed by `SHA-256(orbyn/log-account/v1 ‖ service public key)` (key-service.md);
- the **identity map**, keyed by `VRF(normalised email)` (sharing.md).

Each is a **path-compressed sparse Merkle tree** (SHA-256, only branching nodes and leaves stored), with membership and non-membership proofs. In 3c both exist and are tested with the model of a plain map; **the identity map stays empty**: its root is the empty-tree root, and the VRF (RFC 9381, ECVRF-EDWARDS25519-SHA512-TAI) and the identity statements arrive with sharing. Building the second map now is cheap because the tree is generic over its key, and it keeps the head format final.

**Heads and epochs.** An entry is appended to the log at once but is not visible to lookups until a head covers it. A **head builder** runs on a timer and on demand (a recovery start must reach a cosigned head, step 5). **A cosigned head is made every 10 minutes, even when nothing was appended**: in one transaction it takes the pending entries (possibly none), updates the maps, computes the three roots, builds the head `orbyn/log-head/v1` (size, log root, service map root, identity map root, time in milliseconds, hash of the previous head, log key version), has the HSM sign it with the **log key**, sends it with the entries and map paths to the witnesses, and stores the head with the cosignatures only when the threshold is met. A failed cosign leaves the entries pending and the previous head in place; heads are never half-published. An idle head repeats the size and every root, so it is a new cosignature over the same content, and the **witness's signed time**, not the head's `time_ms`, is what freshness means (below).

**The log key** is a second Ed25519 key in the HSM, separate from the identities (key-service.md), with its own version, pinned by clients with the identity and witness keys. The `Hsm` trait gets `generate_log_key(version)`. The closed message type from 3b is **renamed `HsmMessage`** in this PR (a log key is not an identity), and gains `LogHead`, built only by the head builder; the key used follows the variant (service-key statement or recovery approval: identity; head: log key). So the signing oracle stays closed: no caller can have the log key sign anything but a head. **The log key signs any head the key service builds, including a dishonest one, so it is not the control: the witness is** (next section). Sealing the `Hsm` trait itself is engine#46.

**The witness.** A cosigning service; the shape is the C2SP `tlog-witness` idea (a witness signs a checkpoint after checking it extends the one it signed last) with our own head, because our head carries two map roots, **and the witness verifies the map updates itself**, so it is a check on what the roots say, not only on the log's size.

- **State:** the last size, log root, service map root, identity map root and head hash (see *Witness state, exactly* below for the rest).
- `POST /v1/cosign` with `{head, log_signature, consistency_proof, entries, map_paths}`: the new head; the proof that the log extends; **the entries since the witness's last size**; and, for each entry, the map path (the sibling hashes along its key) as the maps stood before it. The witness checks:
  1. the log signature, against its pinned log key;
  2. the log extends: the consistency proof links its last root to the head's log root, and the entries' leaf hashes, appended to its own accumulator state, give that root (so the entries are exactly the new leaves);
  3. **the map roots are exactly what applying those entries gives**: for each entry, in order, the map path proves the key's old value under the witness's current map root, and the witness computes the new root from the new value; after all entries, `service_map_root` and `identity_map_root` of the head equal the roots it computed, **and nothing else changed**. The value is a function of the entry (its hash and the account's chain length), and the witness checks the entry's `prev` link against the old value, so an entry cannot rewrite an account's earlier chain;
  4. the time rules below.
  The cost is O(k log n) hashes for k new entries, and it needs no database: the paths come with the request.
- **What it signs:** `orbyn/log-cosign/v1 ‖ head hash ‖ the witness's own time`, with its Ed25519 key. It returns the signature and the time.
- **Freshness without new content.** A head with the **same size and the same roots** as the last one is re-cosigned, with a new witness time. That is how an idle log stays fresh. **Freshness is defined from the witness's signed time**, never the head's `time_ms`, which the key service writes: a device or the key service judges "how old is the newest cosignature" by that time. The head's `time_ms` must be no earlier than the last head's and within 5 minutes of the witness's clock. **A witness clock off by more than 5 minutes therefore stops heads (a liveness risk):** witnesses and the key service run NTP, a refusal names its reason (`clock_skew`, `fork`, `rollback`, `bad_proof`, `map_mismatch`), and the key service alerts its operator after 3 refused intervals (30 minutes), well before any device's 2-hour bound.
- **Refusing a fork.** "A second, different head of the same size" means **a different log root or different map roots** at a size the witness already signed; a different time alone is not different. It is refused with the head it holds, so the refusal is evidence.
- **Threshold.** The key service takes `ORBYN_KS_WITNESS_THRESHOLD` cosignatures and clients pin the witness keys and the same threshold. **The threshold must be above half of the pinned witnesses** (2 of 3, 3 of 5, 1 of 1): the key service **refuses to start**, and a client **refuses a head**, under a lower one, because two disjoint minorities could then each sign a different head. It ships with one witness and a threshold of 1, the code and the head format carrying a list. **A self-hoster's own witness gives no fork resistance**: the operator controls both ends, so the pinned witness only guards against the operator's own mistakes; real resistance needs a witness someone else runs (key-service.md says the same). With no witness configured the key service runs but cannot publish a head, and recovery stays refused.
- **State on disk.** `orbyn-witness` writes its state and **`fsync`s it before answering**: a cosignature that was returned but lost on a crash would let the operator present an older head afterwards. It **refuses to start without a state file** unless given an explicit bootstrap flag, so an emptied directory cannot be passed off as a new witness. **It never trusts a map root an operator supplies**: the map proofs are sound only for roots built by `update` from the empty map (`orbyn_translog::map`, module docs), and a hand-built root can show a present key absent. So a new witness **bootstraps from the empty map** (size 0, both map roots `map_empty_root()`) and replays the log from its first entry, or, to start later, **replays the whole map from the log's entries** and checks that the log root it computes is the pinned one; the pinned head fixes a size, a log root and a head hash, never a map root, and the witness signs only once its own recomputed roots match the head's. The state is backed up with the witness's key; a restored older state is the one thing that would let a witness sign a head it had refused, so a restore is a recorded, deliberate step.
- **Clients and the witness.** A device fetches the newest cosignature **directly from a witness** as well as from the key service. Different roots at the same size, from any source, mean a **fork**. A key-service head that lags the witness's newest cosignature by **more than 3 intervals (30 minutes)** counts as **withholding**; lagging by less is normal (the witness signs before the key service stores, and heads are edge-cached for a minute).
- **The witness as a public endpoint.** `GET /v1/cosignature` returns its newest cosigned head. It is cached at the edge for up to a minute (content changes every 10 minutes) and limited per address (60 an hour). The witness sees the addresses of devices that fetch from it; this is added to the metadata in sharing.md. A small witness (a Raspberry Pi) sits behind a caching proxy.
- **Cosign size.** A cosign request carries at most 1000 entries. A witness that is behind catches up in chunks: the key service signs a head for each chunk, and the witness checks each in turn and moves its state to it. **A witness gives no cosignature for a head on the way** (a request marked `intermediate`: it answers 204 with no body); it signs only the head that ends a request, and only within its clock window, so an intermediate head never yields a signature. With three witnesses and a threshold of two, a lagging witness catches up on its own while the other two keep heads flowing.
- **Witness state, exactly.** The last size, log root, both map roots, the last head's hash, and the log's **right edge** (the O(log n) frontier from orbyn-translog's accumulator), so the witness can extend the log root from the entries without asking for anything else.
- **What the code settled** (`orbyn-witness`): each request entry carries `chain_len`, the length of its account's chain before it (the map value is `map_value(entry hash, chain length)`, so the witness cannot check an entry's `prev` link without it); the state also keeps the last head's `time_ms` (for the rollback rule); and a refusal's reason code is one of `clock_skew`, `fork`, `rollback`, `bad_proof`, `map_mismatch`, plus `bad_signature` (not a pinned log key, or no match) and `bad_request` (the wrong number of entries, or an idle head carrying some). The very same head asked again is cosigned with a new witness time and changes nothing.
- **The service, the binary and the client** (`orbyn-witness`). `POST /v1/cosign` takes a canonical binary body (`wire`: version byte, an `intermediate` byte, the 165-byte head, the log signature, the consistency proof, then each entry with its chain length and map path; a trailing byte, a count past 1000 or an entry that does not decode is refused whole, 400 `bad_request`) and answers the 104-byte cosignature for the head that ends a request (200), **nothing at all (204) for an `intermediate` one** (checked, accepted and saved, never signed), or a refusal as JSON (`reason`, a fixed `detail`, and for a fork the head held): 409 for `fork` and `rollback`, 422 for the other reasons. Anyone may post, because a head is cosigned only when the pinned log key signed it. The body is limited to **16 MiB** (1000 entries averaging about 16 KiB with their paths; an entry may be up to 64 KiB, so **the key service ends a head's stretch at 1000 entries or 16 MiB of request, whichever comes first**), a request has one minute to arrive and be checked, and at most 4 are checked at once (503 `busy` beyond that). `GET /v1/cosignature` answers the newest head, the log key's signature and **the witness's own newest cosignature** (`Cache-Control: public, max-age=60`, 10 seconds to answer, 404 until the first head). **It is read from the witness's saved state itself**, which holds the whole signed head and is `fsync`ed before any answer, so it can never show a head the state does not end on; after a restart the witness signs the saved head again with the time then. Reads are limited to **60 an hour per IPv4 /24 or IPv6 /64** (an IPv4-mapped address counts as its IPv4), and the limiter remembers at most 10,000 blocks, dropping the oldest. Behind a caching proxy every read comes from the proxy's address, so the limit is the proxy's, and the proxy's one-minute cache is what keeps real readers under it. The witness cosigns its newest head again **on its own schedule** (every 600 seconds by default). `orbyn-witness` (no subcommand) needs `--bootstrap-empty`, or `--bootstrap-replay FILE` with **`--pin-head HEX`** on the one start that has no state, and refuses it on any other start. **`--pin-head` is the whole signed head, as the key service publishes it, in hex: the head's 165 bytes and then the log key's 64-byte signature.** A replay checks the log signature against the pinned log keys, the size, the log root and **both** map roots it recomputes, and takes the head's hash and time from it, so nothing in a pin is trusted unchecked; the head is kept whole in the state. `orbyn-witness keygen --out FILE` makes the signing key (mode 0600, never replaced), and **a key file that group or others can read is refused**; the seed and its hex are zeroized after use. Its text for an operator (help, start-up errors, log lines) is in `messages.rs`. Settings are flags or `ORBYN_WITNESS_*` environment variables (`BIND`, `STATE_DIR`, `KEY_FILE`, `LOG_KEYS`, `RECOSIGN_SECS`, `NEWEST_PER_HOUR`); the bootstrap flags are never environment variables. **Time rules.** The head that ends a request must be within 5 minutes of the witness's clock; a head on the way to it (`intermediate`, set by the client on every head but the target) may be older, since a witness that was away must walk the chain, but never earlier than the last head's and never more than 5 minutes ahead of the clock. **An intermediate head is never presented as current.** The witness keeps the head it last accepted for the chain's linkage (a later head must name it), and separately **the last head it accepted as final**, saved in the same `fsync`ed state. `GET /v1/cosignature` and the witness's own re-cosigning use only the final one: a one-day-old head accepted only as an old stop on a catch-up is kept, but is never served as newest and never cosigned again. A head asked for again as final, and within the skew, becomes the final one (and is saved before it is answered); a flag byte other than 0 or 1 is refused as a bad request; a pinned head from a replay counts as final only when it is within the skew of the clock then. **Saving the state, per system.** The state is written to a temporary file, flushed, and renamed over the old one, so a reader or a crash sees the old state or the new, never a torn one. **On Unix** the directory is flushed too, and a failure to flush it is an error, so a returned cosignature is never lost to a crash. **On Windows** the file is flushed (`FlushFileBuffers`) and the rename replaces the old file in one step (`MoveFileExW` with `MOVEFILE_REPLACE_EXISTING`, which is what `std::fs::rename` does; a refusal while another handle holds the target is tried again a few times), but a directory cannot be opened as a file to flush the way Unix does (it needs `FILE_FLAG_BACKUP_SEMANTICS`, and a flush may be refused anyway), so the directory flush is attempted and **not required**: NTFS journals the rename, but a crash in the instant after a save returns could in principle leave the previous state. That is the one outcome a witness must avoid, so a Windows witness is for development and CI, not for a witness that others rely on. The address is bound **before** any state is written, so a witness that cannot listen leaves no state behind. **A catch-up cut short resumes.** `GET /v1/cosignature` stays final-only, so after an interrupted catch-up the witness's chain is ahead of the head it serves. A **rollback refusal carries the head the chain stands on** (`held.head`, the head and its log signature, as a fork refusal carries its held head) and the client resumes from it, once per run; if that head already is the target, the client asks for it as final. A state file of another format is **older** or **newer** by the version in its tag (`orbyn/witness-state/v<N>`), each with its own start-up error; a bad checksum is still damage. The cosign permit (at most 4 at once) is taken by the outermost layer **before the request body is read**, so at most four bodies of 16 MiB are ever buffered and the fifth is told 503 `busy` without a byte read. The client cuts off any answer, with or without a Content-Length or a false one, at 16 KiB. The client side (`orbyn_witness::client`) pins the witnesses and the threshold (`Cosigner::new` refuses a threshold at or below half and any key pinned twice) and gets a head cosigned by all of them at once, each on its own: **the key service keeps one chain of heads, each naming the one before it and carrying at most 1000 entries (and 16 MiB) more than it** (it log-signs an intermediate head wherever a stretch is longer), because a witness cosigns a head only when it names the head the witness last cosigned. A lagging witness therefore walks the same chain every other witness walked, `RequestSource::next` giving the request for the head after the one it holds, while the current witnesses answer in one request; the head counts as cosigned when enough pinned witnesses returned a cosignature that verifies under their pinned key. The client reads at most 16 KiB of any answer. Tests run the service in process and the real binary on localhost.
- **A test witness for CI.** `TestWitness` is in-process, with an injectable clock and the same checks as the real one, including the map check (it recomputes the roots, so a key service that changes a map without an entry, or an entry without its map change, is caught). A second set of tests runs the real `orbyn-witness` binary on localhost. Tests: a good head is cosigned; an idle head is re-cosigned with a new witness time; a fork (a different root at a signed size), a rollback, a stale or future `time_ms`, a bad log signature, a bad consistency proof, a map root that does not match the entries, an extra or missing entry, and an entry that rewrites an earlier chain are each refused; a threshold at or below half is refused at start; with three witnesses and a threshold of two, one down still gives a head and two down does not; the witness's state survives a restart and a missing state refuses to start.

## Freshness and monitoring

- **Cadence.** A cosigned head every 10 minutes (above).
- **Three outcomes, kept apart.**
  - **Possible withholding:** a successful response carrying a head whose witness-signed time is more than **2 hours** old, or a key-service head lagging the witness by more than 30 minutes. The device warns of a possible takeover, as for an unknown recovery.
  - **Availability:** failed fetches (network errors, 5xx, a 429 from the witness or the key service, offline) are not a takeover signal. They are left to the 24-hour dead man's switch, and a failed fetch never blocks sync.
  - **Fork:** different roots at the same size, from any source. The device warns at once.
- **The 24-hour alarm is separate.** The dead man's switch (the local notification a successful check reschedules for 24 hours ahead) is about the device not being able to check at all, and stays as written. **24 hours > 2 hours holds**: a device warns at 2 hours of stale heads and the switch fires at 24 hours of no successful check.
- **Recovery's 72 hours** are measured from the witness's signed time in the first cosigned head that includes the start (key-service.md), not from the head's `time_ms`.

## The head publisher (PR 5b)

PR 5 left a gap: `Store::build_head`, `KeyService::sign_head` and `Cosigner` exist and nothing runs them. Until this lands a running service never publishes a head, so `head_covers_entry` is never true and slices 6 and 8 have nothing to serve. This section settles how it runs, in the order it will be built.

**Where it runs.** A task inside `orbyn-keyservice serve`, started after the migrations check and the identity check. With no `ORBYN_KS_WITNESSES` **it does not start**, the service runs, certifications and retirements are still appended, and no head is ever published (recovery stays refused, as above). Only `ORBYN_KS_IDENTITY_VERSION` has a default: **with witnesses set, the keys, the threshold, the log key version and the interval are required** (an unset one is the designed "is not set" error). The log key is made by `orbyn-keyservice init-log-key` (log key 1). Settings: `ORBYN_KS_WITNESSES` (comma-separated URLs; `https` only, except a loopback address for development), `ORBYN_KS_WITNESS_KEYS` (the pinned public keys, hex, in the same order, no key twice), `ORBYN_KS_WITNESS_THRESHOLD` (above half of the pinned witnesses), `ORBYN_KS_LOG_KEY_VERSION` (the log key must exist in the HSM) and `ORBYN_KS_HEAD_INTERVAL_SECS` (from 60 to 900 seconds: a longer interval would break the 30-minute lag bound below). `serve` refuses to start on any of these that is wrong, using `Cosigner::new`'s own refusals for the threshold and duplicate keys. One publisher runs per database. A second one is safe, never wrong: the store's write lock and `prev_head_hash` uniqueness make the later commit lose (`HeadSuperseded`), and it does nothing that cycle.

### A head is signed first, cosigned after

**The crash window.** If a head is stored only after the witnesses cosigned it (the order above), a crash between the cosignatures and the store leaves the witnesses standing on a head the key service does not have. The next head, built on the old last head, names a different previous head, and every witness refuses it as a fork. The head could be rebuilt identically only if nothing new was appended meanwhile, which cannot be promised. So the order changes:

1. The head is **built, signed with the log key and stored first**, with no cosignatures. It is now part of the chain, whatever happens next.
2. The witnesses are asked to cosign **that stored head**. Nothing newer is built until it has enough cosignatures; a restart finds the newest stored head and goes on cosigning it.
3. Cosignatures are rows in a new append-only table `head_cosignatures (head_id, witness_key, cosignature)`, and a head is **published** when `published_heads` (a second append-only table, one row per head, written once) says so: when at least the threshold of pinned witnesses have a verified cosignature of it. Migration 0003 adds both, with the same grants and triggers as the other tables; `heads.cosignatures` stays in the schema and is unused.
4. **What is public is only the newest published head.** `head_covers_entry` becomes true only when a published head covers the entry, not when a stored one does. The public API (PR 6) serves a head only once it is published, and never a stored head that has no cosignatures.

**This changes the rule PR 3 and 4 wrote down.** They said a head is "stored only when cosigned"; it is now **stored when signed and published when cosigned**. What devices and the public API treat as authoritative is the **published** head only: the newest row of `published_heads`, never a stored head that is waiting for its cosignatures, and `head_covers_entry` follows it. A stored head is an internal link of the chain, nothing a client may rely on. `Store::commit_head` stores a signed head and no longer takes the cosignatures; `Store::add_cosignature` and `Store::publish_head` are new. The chain has no branches: no two heads name one previous head (the database refuses it), so the witnesses never see a fork. **A stored head that is not yet published blocks the next one while it is fresh; once it is too old to be cosigned it is built on, not waited for** (next section).

### The cycle

Every interval (and straight away when the last cycle ended with more entries pending than one head covers):

1. **Build.** `build_head(now, log_key_version, cap)`, at most 1000 entries. Before it is signed, the request a witness will be sent for it is measured (the entries and their map paths): over **16 MiB** the head is built again with half the entries, until it fits, so a head is never cut after it is signed. An idle log builds an idle head (the same size and roots, a later time), which is how it stays fresh. If the clock is behind the last head's time (`TimeRegression`) the cycle is skipped and counted as a refused interval.
2. **Sign, store.** `sign_head`, then `commit_head`.
3. **Cosign.** `Cosigner::cosign_within(StoreSource, head, 2 minutes)`, all witnesses at once, each on its own. **It returns as soon as the threshold of valid cosignatures is in, without waiting for the rest**, and gives up on whoever is still answering at the 2-minute deadline: one slow witness cannot hold the others back or stop the cycle. A witness let go that way counts as not reachable for this cycle and is asked again in the next (what it had already accepted stands, so it goes on from where it got to). The same deadline ends a cycle that is below the threshold.
4. **Publish** when `cosigned_enough` holds, after recording each verified cosignature. Otherwise the head stays stored and unpublished. **The next cycle goes on with the same head only while it is fresh (at most 4 minutes old); an older one is built on, not waited for.** A witness accepts the head that ends a request only within 5 minutes of its own clock, so a head left waiting longer than that can never be cosigned as the last one, and waiting on it would stop heads for ever (the interval is up to 15 minutes, so with witnesses away across even one interval every retry would find the head stale). So: the next head is built on top of the stale one, named by its `prev_head_hash`, and a witness is walked through the stale head as an *intermediate* head (those may be old) to the new one, which is within its window. **The chain stays one line** (no two heads name one previous head), **the stale head is never published itself** (what is published is always within the witness window when it is published), and the entries it covered are covered by the newer head that is. A restart soon after a crash (within the 4 minutes) finds the fresh stored head and cosigns that same head.
5. **A backlog** (more than 1000 entries pending after a publish) runs the next cycle at once, so a long outage does not take 10 minutes per 1000 entries to clear.

### The request source

`StoreSource` implements `orbyn_witness::client::RequestSource` over the stored chain of heads. `next(after)` returns the request for the stored head that names `after` as its previous head (the first stored head for `None`): the head, its stored log signature, the **consistency proof** from the previous head's size to its size, and for each entry in between, in order, its chain length and the **map path as the maps stood before it**.

- **Consistency proof.** Every hash in an RFC 9162 consistency proof is the root of an aligned complete subtree, which `log_nodes` stores, so it is read, not recomputed (`Store::consistency_proof(old, new)`, checked against `orbyn_translog::merkle::consistency_proof` over a model for every pair up to a small size).
- **Map paths.** From the previous head's two roots, for each entry in order: `MapStore::prove` the key under the current root, keep the path, then `orbyn_translog::map::update` for the next root. Nothing is written; the nodes are the ones `build_head` already wrote, content-addressed, so any old head's roots still answer. The final roots must equal the head's, or the source fails (`Corrupt`) instead of sending a request the witness would refuse.
- **A witness the chain does not contain.** If `after` is not a stored head, the source fails for that witness. That witness holds a head the key service never stored, which is evidence of a fork or a wrong pin, and is reported (below). The others are unaffected.
- **Idle heads.** A witness that was away for a day walks about 144 idle heads, one request each; that is the cost of keeping the chain one line. **Progress along the chain is the head named by `prev_head_hash`, never the size**: an idle head has the size of the head before it, so the catch-up (`orbyn_witness::client`) counts a step as moving when the head is a new one (not the one it came from, not past the target) **and within a bound of 1000 steps for one run**; a witness further behind is brought forward over several runs, each leaving it where it got to (the witness keeps what it accepted). PR 5b fixes the first version of this guard, which took a head at the target's size as going nowhere and so could never walk a chain with idle heads in it.

### Witnesses down, slow or refusing

- **Threshold met.** The head is published. A witness that did not answer is simply behind and walks the chain when it returns.
- **Below the threshold.** The head stays stored and unpublished (and is built on once it is stale, as above); the previous published head stays the newest the public API serves, so its witness-signed time ages. New certifications and retirements are still accepted and appended (they wait for the next published head); `head_covers_entry` stays false for them.
- **Refusals are evidence, not noise.** A `fork`, `map_mismatch` or `bad_proof` refusal, or an invalid answer, is logged with the witness's index, the refusal's code and the head it holds if it sent one (machine-only fields), and counted separately from a witness that could not be reached.
- **Alerts** (structured log lines, machine-only, for the operator's monitoring; no paging system is built here): `head_unpublished` **30 minutes after the newest published head's time** (the process's start only when there is none yet, so a restart does not hide an outage that began before it), and again every hour after, **on a timer of its own that runs beside the cycle** (every minute), so a cosign in flight never holds an alert back, with how long it has been and how many witnesses answered and refused; `head_published` (with `recovered`) when the first head after such a stretch is published. A refusal is logged as `head_cosign_refused` with the witness's index, the refusal's code and the head it holds if it sent one; a witness whose answer is not valid or whose held head is not in the chain is `head_cosign_invalid` or `head_source_failed`.
- **What a device does** is already settled in *Freshness and monitoring*: a published head whose witness-signed time is over **2 hours** old, or a key-service head more than 30 minutes behind the witness, is a possible-takeover warning on the device, and a failed fetch is availability and is left to the **24-hour** dead man's switch. The publisher does not implement either; it is why the interval is capped at 15 minutes and why witnesses down for **more than two hours** become a visible warning on every device even though nothing was taken. The runbook (PR 7) says so.
- **Witness clock.** A witness refusing for clock skew (`clock_skew`) counts as unreachable for the threshold and is reported with that code.

### Tests (PR 5b)

Run against real `orbyn_witness` services in process (three witnesses, threshold 2) and a real Postgres:

- A certification is in the next published head, and `head_covers_entry` is false while the head is stored and unpublished (witnesses down), true after.
- 2 of 3 witnesses up: published; the third, started later, walks every stored head (idle heads, heads with entries) and cosigns the newest.
- A backlog of more than 1000 entries: published in several heads without waiting an interval between them; a request over the 16 MiB cap is rebuilt smaller before it is signed.
- **The crash window:** the process stops after a head is stored and before any cosignature; restarted, it cosigns the same head, builds nothing new, and entries appended during the stop go into the head after it. The same with a stop between two witnesses' cosignatures.
- Below the threshold: no publish, retried each interval, the older head still the newest published; `head_unpublished` after 3 intervals; a witness returning catches up.
- A witness that holds a head the key service never stored: the source fails for it, the refusal is reported, the others still publish.
- A fork attempt (two heads naming one previous head, forced by test) cannot be made by the publisher; the store refuses the second.
- `consistency_proof` equals the model for every pair of sizes up to 40; map paths replayed over 200 random entries end on the head's roots; a tampered stored node makes the source fail.
- With no witness configured the publisher does not start, appends still work and no head appears; every invalid setting stops `serve` at start.

### Decisions for the owner

1. **Sign first, cosign after** (the crash window above), which changes PR 3 and 4's "stored only when cosigned" and adds migration 0003. The alternative, keeping the old order and re-sending an identical head after a crash, fails when anything was appended during the stop.
2. **A stored-but-unpublished head blocks the next one only while it is fresh** (at most 4 minutes old, which a witness can still take as the end of a request). A fresher head is the one to get cosigned, and nothing is built on it; **an older one is built on, not waited for**, and the witnesses walk it as an intermediate head. The chain stays one line, the stale head is never published itself, and nothing older than the witness window is ever published (see *The cycle*, step 4).
3. **Interval cap of 15 minutes** and the 30-minute alert, tied to the 30-minute lag bound already settled for devices.
